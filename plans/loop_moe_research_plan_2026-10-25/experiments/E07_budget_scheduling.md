# E07：跨请求预算分配与收益指数

**可作为E03的部署扩展；只调当前可见请求；不预设Whittle指数理论适用。**

## 科学问题

固定总专家调用预算时，将额外计算给预计收益更高的当前请求，是否优于每个token相同深度？[Alloc-MoE](https://arxiv.org/abs/2604.08133) 已有预算分配，[SeqTopK](https://arxiv.org/abs/2511.06494) 已有序列级选择，因此需要明确在线语义与累计约束。

若暂停时token隐藏状态不变化，它并非自动是restless bandit；多个请求通过容量/价格耦合也不满足经典独立arms的条件。本实验使用“收益指数启发式”，不使用未经证明的Whittle/Gittins最优性名称。

## 两个可分开实现的场景

**A：同一服务窗口的当前请求前沿。**N={8,32,128}个请求，每个已有至少一轮，剩余总预算B_group是Top-2调用组的数量，动作是选择某个活跃请求再计算一轮。当前选择改变该请求状态与下一步收益，其他请求暂停。

**B：流式逐token预算账本。**每来一个新token补给K个expert credits，余量R_m=R_{m−1}+K−q_m≥0。过去已执行调用不可撤销；可限制carryover上限防止长期积攒导致突发。若设carryover上限，溢出的预算作废不计为已执行。初始R_0=0且每token至少一轮Top-2时，K≥2；E=4,K=1的SeqTopK反例仅为原公式核查，不是此系统的默认配置。

论文中两个场景分别报告，不能把服务窗口最优分配解释为未知未来序列的最优分配。

## 具体规则

收益指数 \(I_i=\widehat\Delta_i/\widehat c_i\)。主单步版本用下一步改善Δ1与下一步成本c1；tail版本用完整π0尾迹改善Δtail与完整尾迹成本c_tail；两步包版本用Δ2/c2。不得把累计终局收益除以单步成本后称单步边际收益。cost先用实际expert calls（相等成本），再用校准的增量时间。预计Δ≤0时不强行花完预算，报告实际使用量；与必须用满的baseline比较时给等实际成本曲线。

对每个活跃请求更新h后重算I。tail指数按一步执行再重算只作为启发式，不能继承固定计算包的最优性；如承诺执行完整包须一次预留完整成本。最小服务约束保障每请求至少一次基本FFN；额外计算按指数选。硬账本检查独立于预测器：余量不足无法执行；价格不能替代这一检查。

## 可执行步骤

1. 先在E08的N≤8,H≤4有限模型上，用精确DP计算最优预算分配，评价指数启发式的gap。
2. 构造两类收益轨迹：边际收益递减、先投入后获益。后一类揭示贪心ratio可能失败；不能删除这种失败样本。
3. 从E03校准好的Δ控制器建立实际LM服务窗口；先64请求×4预算档做trace replay。
4. 在请求重排、batch size变化、长度/领域混合变化下评估。分配器不能读取未来token或y。
5. 真正GPU执行时把同一轮继续的请求分桶合并；记录grouping开销与新排队。
6. B场景验证每一个prefix的累计已执行q≤K·m；保存整条账本而非只看全序列平均。

## 对照

| 对照 | 作用 |
|---|---|
| 等深度、round-robin | 基础公平分配 |
| 随机额外分配 | 控制预算本身 |
| entropy/隐藏变化指数 | 便宜启发式 |
| 学到的Δ/c指数 | 主启发式 |
| 预算条件小MLP | 不显式使用ratio |
| 小问题精确DP | 只作可计算范围上界 |
| 完全知晓y/未来的oracle | 标为离线上界，不参与部署胜负 |
| 固定两步包的预测收益 | 检查延迟收益导致的指数失败 |

为区分长期与一步收益，固定路由时比较另行标注的单步Δ1、E03/E02完整tail收益和固定两步计算包Δ2。两步包成本为两次Top-2，必须扣除4个expert credits。

## SeqTopK公式的预算审查

公开v2式(7)的prefix top-mK集合不能撤回过去调用。E=4,K=1，分数(.40,.30,.20,.10)后接(.49,.48,.02,.01)，会执行1+2=3次、超过前缀预算2。这是本次对公开公式的反例，未审查其仓库实现，不能写成作者承认的代码bug。

本方案只依据实际已执行调用扣账，不依据每轮重新计算的“虚拟历史竞争”数额。脚本与理论文件给出反例和账本归纳证明。该修复是研究正确性要求，是否有独立论文贡献仍需完整文献检索。

## 评价与限制

质量：总体token加权NLL、每请求NLL、难易分层与低频请求表现。资源：累计/逐prefix预算违反量（必须0）、平均及p95延迟、请求等待、吞吐、实际预算使用率。

如果吞吐改善但p95恶化，必须报告而不能只选一个指标。每请求质量下界/公平性约束可以作为可选优化，但不承诺由平均NLL保证每请求质量。

1卡可跑全部小型实验，3卡做seed；初筛≤24 GPU-hours。若比例指数不如简单等深度，先检查收益是否递减、时间预测是否可靠；可转为固定两步包/小窗口DP，而不是无证据地引入restless bandit求解器。

输出：DP-gap曲线、硬账本轨迹、延迟收益失败案例、质量—预算—延迟表、请求重排敏感性。
